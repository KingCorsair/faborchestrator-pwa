# Device stamp feasibility: non-exportable Web Crypto key in the installed PWA

**6 October 2026. Jothi's Option 2: FO-managed one-time device enrollment.**
This decides only how the device stamp is implemented. Candidate:
`DEVICE-nnn` + an ECDSA P-256 private key generated by the installed PWA with
`extractable: false`, the `CryptoKey` itself kept in that PWA's IndexedDB, proved
by signing fresh server challenges. Entra/Intune are outside this work.

The working cookie implementation (`docs/DEVICE_ENROLLMENT.md`) is unchanged.
Nothing here is deployed or connected to the real device store.

The page shows: credential present/absent, public-key fingerprint, created
when and in which context (installed app or browser), a restart history (what
every page load found), storage-persisted state, browser/context details, and a
result log. Buttons: Generate Device Credential, Check Stored Credential, Sign
Test Challenge + Verify Signature, Replay Last Signature, Request Persistent
Storage, Scan QR (inside this app), Clear Test Credential, Clear Restart History.
It never shows or exports private key material; it does try to export it once,
to prove the browser refuses.

Two test QR codes are on the page: an **enrollment-style** one
(`/device-crypto-test?enroll=TEST-…`, a throwaway value) and the **normal FO
QR** (`/`). Scanned with the in-app scanner they run, respectively, "make a key
here and prove it" and "prove the key → would continue to FO sign-in, or BLOCK".
Opened with the phone's own Camera instead, the enrollment one lands in the
browser and the page says so in red: that is the iPhone mismatch, made visible.

## Results so far (this machine)

| Check | Chromium | WebKit (Playwright, Windows) |
|---|---|---|
| Generate P-256 key, `extractable: false` | ✓ | ✓ |
| Store the `CryptoKey` in IndexedDB and read it back | ✓ | ✓ |
| Export of the private key refused (pkcs8, jwk) | ✓ | ✓ |
| Sign a server challenge; Node verifies (IEEE P1363) | ✓ | ✓ |
| Replay of a used signature refused | ✓ | ✓ |
| Same key after **3 full browser restarts**, each signing a fresh challenge | ✓ | ✓ |
| Cleared → unenrolled → device check would BLOCK | ✓ | ✓ |
| In-app scanner reads the enrollment QR (fake camera), key made and proved in the same page | ✓ | — |
| After restart, in-app scan of the normal QR proves the same key | ✓ | — |
| Never-enrolled context scanning the normal QR → BLOCK | ✓ | — |

26/26 restart checks, 9/9 scanner checks, 12 unit tests (fresh, one-use,
expiring, key-bound and purpose-bound challenges; wrong curve, wrong key,
tampered and replayed signatures refused; a non-exportable key cannot be
exported **or wrapped**).

**What this does not prove.** Playwright's WebKit on Windows is not Apple's
WebKit. It did *not* reproduce the known iOS failure (Safari private browsing
refuses to store a `CryptoKey`, `DataCloneError`, because Apple's WebKit
encrypts stored keys with a per-site key it cannot get in an ephemeral session).
So the **iPhone Home Screen app result can only come from a real iPhone.**

## Running it on real phones (no deploy)

The phone needs HTTPS (Web Crypto, the camera and installation all require a
secure context). A Cloudflare quick tunnel to this computer gives one:

1. `cloudflared tunnel --url http://localhost:3013` and note the
   `https://….trycloudflare.com` address it prints.
2. In the repo, with that address:
   `npm run build`, then start with
   `DEVICE_CRYPTO_TEST=1 PUBLIC_ORIGIN=https://….trycloudflare.com npx next start --port 3013`
   (plus the usual `SESSION_SIGNING_*`, `FABORCH_BASE_URL`, `SEAT_STORE_PATH`
   from `.env`). The test needs no FabOrchestrator.
3. Open `https://….trycloudflare.com/device-crypto-test` on the computer too:
   it shows the two test QR codes.

The tunnel address changes every time; an installed test app is tied to it.
Reinstall after a new tunnel. Alternatively, with approval, set
`DEVICE_CRYPTO_TEST=1` on the hardening app for the duration of the test.

### iPhone

1. Safari → the test URL → Share → **Add to Home Screen** (name: FO Crypto Test).
2. Open **FO Crypto Test** from the Home Screen. "Status in this context" must
   say **installed-app**.
3. **Generate Device Credential** → expect "Key generated … stored in IndexedDB
   and read back" and "Private key export refused".
   (If it says `FAILED at store: DataCloneError`, the design does not work in
   this context. Stop and report.)
4. **Sign Test Challenge + Verify Signature** → "Signature verified by the
   server". **Replay Last Signature** → "refused".
5. **Request Persistent Storage**; note the answer.
6. Fully close the app (swipe it away in the app switcher).
7. Reopen it from the Home Screen → expect "Key loaded after restart: <same
   fingerprint>"; restart history gains a `usable-key` line.
8. Sign + Verify again → verified.
9. Repeat 6–8 twice more; also once after locking the phone for a few minutes,
   and once after rebooting the phone.
10. **Scan QR (inside this app)** → allow the camera → point at the
    enrollment-style QR on the computer → "Enrollment-style QR scanned inside
    the installed-app", proof verified. Then scan the normal FO QR → "Device
    proof OK → production would continue". The app never switches to Safari.
11. Control: scan the enrollment-style QR with the **Camera app**. It opens in
    Safari; the page says "This is the browser, not the installed app" and shows
    no credential, although the installed app has one. That is the storage
    separation.
12. Optional, important for deciding re-enrollment rules: back up and restore
    to another iPhone (or note whether the app survives an iOS update) and
    record whether the key is still there.

### Android (Chrome)

1. Chrome → test URL → menu → **Install app** (or Add to Home screen).
2. Open the installed **FO Crypto Test**; context should say installed-app.
3. Steps 3–10 as for iPhone.
4. Control, expected to differ from iPhone: scan the enrollment-style QR with

and a screenshot of the restart history.

## Findings

**Can Option 2 work this way?** Yes in principle, and verified in Chromium and
desktop WebKit. **On iPhone it depends on one fact only a device can show:**
whether a Home Screen app keeps a non-exportable `CryptoKey` in IndexedDB across
restarts. Everything else on iPhone is supported: Web Crypto ECDSA, IndexedDB,
camera access in Home Screen apps (iOS 14.3+), and Home Screen apps are exempt
from Safari's 7-day storage deletion.

**iPhone.** Enrollment and every device proof must happen inside the installed
app, using its own scanner. iOS opens Camera-scanned links in Safari, never in a
Home Screen app, and Safari's IndexedDB is separate from the app's. Everyday
access is "open the app" (its start page runs the device proof); an operational
QR, if used, is scanned inside the app. Camera permission may be asked again
after navigation in a Home Screen app, so keep scanning on one screen.

**Android.** A Chrome-installed app shares Chrome's storage, so a Camera scan
that opens in Chrome or in the app reaches the same key. Use the same in-app
flow anyway for one consistent design; Camera scanning is a convenience that
also works there.

**No weaker fallback is built in.** If a platform cannot persist the
non-exportable key, the alternatives are all weaker and would be a separate
decision:
(a) an exportable key stored as data (any script on the origin could read and
copy it: no better than a bearer secret);
(b) the current bearer cookie;
(c) WebAuthn platform credentials, which on Apple and Google are generally
synced passkeys (not device-bound); device-bound variants exist but are not a
reliable default from a PWA on both platforms.

## Security notes for the production design

- **Same-origin script can use the key.** `extractable: false` stops export,
  not use. Any script running on this origin while the app is open can call
  `crypto.subtle.sign` with the stored key, and FabOrchestrator's own pages are
  served on this same origin through the gateway. So an XSS in FabOrchestrator's
  pages, or a third-party script either app loads, could answer challenges
  while it runs, though it cannot take the key away. Mitigations: purpose-bound,
  60-second, single-use challenges; the proof only at entry/sign-in (so a stolen
  proof buys one sign-in attempt that still needs the user's password); a CSP
  with no third-party script sources on the device pages; and keeping the plan's
  accepted risk G10 in view. A separate origin for the device check would remove
  FabOrchestrator's pages from that origin; that is an architecture change to
  weigh, not a default.
- **CSP.** The device pages keep `default-src 'self'`, `frame-ancestors 'none'`;
  an in-app scanner using zxing-wasm needs `'wasm-unsafe-eval'` (tested).
- **Storage clearing / eviction / uninstall.** Any of these deletes the key, and
  the device is unenrolled: new enrollment QR, new `DEVICE-nnn`. Request
  `navigator.storage.persist()` at enrollment. Removing a Home Screen app on iOS
  deletes its data; on Android, clearing Chrome's site data also clears the app's.
- **Backup / migration.** Undocumented for both platforms; to be recorded in the
  phone test. The design must not depend on it: a restored phone either still
  has the key (same `DEVICE-nnn`, still revocable) or has to re-enroll.
- **Challenges.** 32 random bytes, 60 seconds, single use (spent even on a
  failed attempt), bound to the claimed device and to the purpose. A replayed
  or expired signature is refused (tested).
- **Revocation** stays server-side: a revoked device can still sign, and is
  still refused, because the server checks `DEVICE-nnn`'s status at the proof
  and on every request of the session it bound.
- **Multiple devices, re-enrollment, lost key.** Each enrollment makes a new key
  and a new `DEVICE-nnn`; nothing carries over. A lost key cannot be recovered
  or re-bound from metadata.
- **Not attestation.** This proves "this app installation holds the key it made
  at an approved enrollment", not "this is iPhone serial XYZ".

## Migration plan (only when approved)

Minimum change from the current bearer cookie to Web Crypto + IndexedDB +
challenge-response, keeping the enrollment QR, store, admin screen, allowlist,
audit and revocation:

1. **Store** (`lib/devices/store.ts`): the device record holds the public key
   (SPKI) and its fingerprint instead of a token hash; record version 3; the
   once-only enrollment marker unchanged.
2. **Challenges** (`lib/devices/challenges.ts`, from the test module): issue and
   verify, bound to `DEVICE-nnn` (or the enrollment) and purpose.
3. **Enrollment** (`/device-enroll`, `complete/route.ts`): the installed app
   (in-app scanner, or paste) presents the enrollment code; the page generates
   the key, requests an `enroll` challenge, signs it, and sends code + public key
   + signature. The server spends the enrollment and creates `DEVICE-nnn` with
   that public key. No cookie.
4. **Entry/sign-in** (`components/login-page.tsx`, sign-in route): the page loads
   the key, gets a `verify` challenge for its `DEVICE-nnn`, signs; sign-in is
   refused without a valid proof. The signed session token carries `did`
   (`lib/auth.ts`).
5. **Every request** (`proxy.ts`, `lib/auth/verify-session.ts`, the gateway):
   check the session's `did` is still APPROVED; a revoked device's session stops
   on its next request. Pages before sign-in render only the device check, which
   shows "not approved" when there is no key or the proof fails.
6. **Remove** `__Host-fo_device`, the device-cookie gate and its exemptions;
   keep `DEVICE_GATE` as the switch.
7. **In-app scanner** for the enrollment QR (from the test module), plus the
   paste box as fallback.
8. **Tests**: port `__tests__/devices/` from cookies to proofs; keep the
   race, expiry, reuse, revocation, replacement and log-hygiene cases.
9. **Re-enrollment** of every device after the switch (cookie devices cannot
   become key devices).
