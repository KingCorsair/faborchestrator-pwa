Executive technical summary

The architecture in the exploratory plan is correct. The scope is not: most of it is already built, sitting uncommitted in the working tree, and the two things it gets wrong about FabOrchestrator’s wire format and agent topology are exactly the two things that would have cost a week to discover during implementation.

Recommendation

Consolidate on progressive_web_app_demo/. It is the only one with a proven end-to-end path, a test suite, a design system and a deployment. Retire faborch_pwa/ after lifting its two better ideas (the opaque server-side session id, and not sending model at all so FO picks its own default). Keep FO’s own installability work — it answers a different question (“install the real product on a desktop”) and does not compete with a phone-shaped client.

The first engineering act is a decision, not code: commit or discard. Roughly 3,500 lines of integration work currently exist only in one working tree with no branch, no review and no backup.

One live defect found during inspection

FO’s canonical error envelope is nested: { error: { errorId, type, priority, message } } (lib/errors/api-error-handler.ts:115). The PWA proxy’s messageOf() returns body.userMessage || body.error — which for that envelope is an object. It is typed string, passed to fail(code, error, status), and rendered as a React child in components/fab/screens/agent-chat.tsx. Any FO error that goes through handleApiError — a role-restricted model, an invalid parameter, a 400 — produces a render crash or [object Object] instead of the message. Fixed in WP4.

3.1 Load-bearing facts

  • The proxy hop is mandatory, not stylistic. There is no Access-Control-Allow-Origin anywhere in FO’s app/, lib/ or next.config.ts. A browser call from the PWA origin to FO’s is blocked before it is sent.
  • FO is stateless per turn. convertToModelMessages(uiMessages) builds context from the request body. conversationId only adds FO-side persistence and S3 file refs. The PWA can hold conversation state client-side with no server store on either end.
  • Streaming survives client disconnect. result.consumeStream() at app/api/chat/route.ts:757 means FO finishes the turn and writes its audit rows even if the phone drops. Aborting on the PWA side is safe.
  • Deployment reality. FO production is Elastic Beanstalk behind CloudFront (https://d7y8a8whrch88.cloudfront.net), ALB idle timeout 600 s, Nginx :80 → container :3000. App Runner was decommissioned precisely because its 120 s hard request timeout broke SSE (DEPLOYMENT.md §12). The PWA deploys to Fly with FABORCH_BASE_URL already set to that CloudFront URL in fly.toml:49.

Cannot be proven from source

Whether CloudFront buffers the SSE response and whether the MCP Lambdas are reachable from the EB security group are runtime properties; the 2026-09-01 probes answered both (streaming progressive; the probe account had zero data connections — a provisioning gap, not an infrastructure one). The 2026-08-24 backend-agent question dissolved on verification against upstream e5a5abd: GET /backend-agent 404s because no such surface exists in any upstream branch, not because the deployment is behind. Remaining probes in §16 close at their milestones.

Strictly better than a token-bearing cookie if the store is durable; its own header admits the in-memory map dies on restart. §05

New functionality required

Genuinely new

  • New Artifact detection, extraction and sandboxed rendering in the chat stream (WP9).
  • New Durable PWA session store, replacing the stateless HMAC that cannot be revoked (WP2).
  • New An FO-session liveness probe so the PWA knows the FO token is still honoured, not merely present (WP2).
  • New A normalised error contract between proxy and screen — one {code, message} shape for every failure path (WP10).
  • New Per-agent availability gating on the landing page, driven by /api/modeling-agent/access rather than by a 403 mid-conversation (WP7).
  • New Proxy, agent-routing, artifact-parser and error-path test suites (WP11).

Deliberately not built

  • Any MES query, yield calculation, metric detection or SQL. FO owns it.
  • A UiView spec renderer. FO owns /v/[key]; the PWA links to it.
  • A second system prompt, model picker or MCP picker. Both are decided server-side.
  • File upload into the Modeling Agent’s S3 staging — a separate piece of work with its own storage and access decisions.
  • Offline caching of any /api/ response. A cached downtime figure is a wrong downtime figure.
  • A service worker on the FO path. The constraint holds and the current worker already obeys it.

Scope decision this plan asks the review to confirm

The PWA today carries a second product: a production-order review workflow on a mock MES, with its own login credential (DEMO_USER_*), decision log, barcode scanner, activity feed and rules engine. None of it touches FabOrchestrator. If the goal is “a mobile front door to FO”, that workflow and the demo credential branch in app/api/auth/login/route.ts should be removed — it roughly doubles the surface to be tested, secured and explained. WP2 assumes removal. If the order workflow must stay, add 3 days to the estimate for keeping both credential paths coherent.

WP2Authentication & session architecture2.5 d
Objective
One credential — the operator’s own FabOrchestrator account — exchanged for a revocable PWA session, with the FO token never reaching the handset and the two expiry clocks reconciled.
Why needed
Every FO call is authorised as a specific person: their role, their model allow-list, their MCP connections, their quota, their audit row. A shared service account would hand whoever holds the QR code somebody else’s MES access and make every prompt_audit_logs row attributable to a machine.
What already exists
  • Already implemented FO login forwarding (app/api/auth/login/route.ts), including the distinction between “wrong password” (401) and “FO unreachable” (503) — a real trap, since an operator told their correct password is wrong will spend the demo retyping it.
  • Already implemented httpOnly FO-token cookie with scheme-derived secure (lib/faborch/session.ts).
  • Already implemented Login throttling (lib/rate-limit.ts).
  • Already implemented Cookie drop on sign-out, and on FO 401 inside the chat proxy.
Must be implemented
  • Remove the demo-credential branch. Delete authenticate()/configuredUser() from lib/auth.ts and the first branch of the login route. FO becomes the only identity.
  • Replace the stateless HMAC with an opaque session id. Today verifyToken validates a signed payload with no server record, so logout cannot revoke and a stolen token is valid until exp. New: a pwa_sessions(id, fo_token, user_json, created_at, expires_at) row keyed by a 32-byte id in a second httpOnly cookie. This also lets the FO token move out of the browser entirely — the phone then holds no FO material at all.
  • Reconcile the clocks. PWA TTL currently 12 h; FO idle-evicts at 30 min. Set the PWA session’s expiry to min(FO expiresAt, now + TTL) and treat any FO 401 as terminal for the PWA session, not just for the request.
  • Liveness, not presence. app/api/auth/me/route.ts currently reports faborch: foTokenFrom(req) !== null — whether a cookie exists, not whether FO honours it. Call GET {FO}/api/auth/me and report the answer. Cache it briefly so a page-heavy screen does not fan out.
  • Sign-out. Call POST {FO}/api/auth/logout, best-effort, then delete the PWA row and both cookies. The current code deliberately skips FO’s logout to avoid killing a parallel FO browser tab; with a PWA-only identity that reasoning no longer applies, but it is a product call — flag it for the review.
  • Expiry UX. On any 401, clear local state and route to /login?next=… preserving the destination (lib/return-path.ts already does this).

FabInsight / MES plan

The mechanism is documented in WP8. What the plan commits to, in one place:

The PWA does

  • Ask FO which MCP connections the operator has, every turn (cached briefly), and forward only the ids FO reports as connected.
  • Refuse to send a turn with an empty tool list, and say why.
  • Render whatever markdown comes back — text, tables, lists — in FO’s own type scale, with tables scrolling inside their own container.

The PWA does not

  • Detect that a question is about a metric.
  • Choose a data source, write SQL, or call an MCP server.

A locally run FO can prove the streaming path but may not reach data at all. Two of the ten MCP servers were returning HTTP 500 on 2026-07-24. §14

Error & progress handling plan

The full mapping table is in WP10. Two rules govern it.

One shape crosses the boundary

{ code: PwaErrorCode, error: string, errorId?: string }. error is always a string, asserted by a property test over arbitrary FO bodies. Components never receive an object, never receive undefined, and never have to guess.

The current implementation violates this — FO’s nested envelope passes straight through messageOf(). That is the first fix in WP4.

Three progress states, not one spinner

  • Waiting — request sent, no frame yet. Dots.
  • Working — a tool is running. Dots + the tool’s own name. An operator watching a fifteen-second pause needs to know something is being looked up, not that the app hung.
  • Answering — text arriving. Dots off, cursor on.

Plus a fourth, negative state: stalled, after 45 s with no frame of any kind — three missed keep-alives.

16.2 The smallest experiment that proves the architecture

Two experiments, in order. The first needs no code at all and eliminates the two largest unknowns.

E0 — Prove the wire format and the streaming path, with curl

Minimum auth: one FabOrchestrator account. Nothing else.

TOKEN=$(curl -s -X POST "$FO/api/auth/login" \ -H 'Content-Type: application/json' \ -d '{"email":"…","password":"…"}' | jq -r .token) curl -s "$FO/api/mcp/connections" -H "Authorization: Bearer $TOKEN" \ | jq '[.[] | select(.status=="connected") | .id]' # → IDS curl -N -X POST "$FO/api/chat" \ -H "Authorization: Bearer $TOKEN" \ -H 'Content-Type: application/json' \ -H 'Accept: text/event-stream' \ -d '{"messages":[{"role":"user","parts":[{"type":"text", "text":"Reply with the single word: ready"}]}], "activeMcpIds":IDS}' -D -

Pass: response headers show content-type: text/event-stream and x-accel-buffering: no; data: lines appear progressively, not in one burst at the end; frames are text-delta with a delta field; the stream ends data: [DONE].

Failure readings. Nothing until the end → something between you and FO is buffering (run it against the origin EB URL as well as CloudFront to find out which). Frames named text with a text field → a different ai version than the parser assumes; re-pin the tests. 401 → the token was idle-evicted; log in again. Empty IDS → stop and get MCP connections assigned to the role before writing anything, because every subsequent data answer would be meaningless.

Cost: 30 minutes. Value: settles the SSE format, the buffering question and the MCP provisioning question before a single line is written.

E1 — Prove the full architecture, PWA frontend → PWA backend → FO → screen

Minimum auth: the FO account from E0, plus a PWA session, because /api/faborch/[agent]/chat is behind requireAuth and the FO token is read off the request. There is no shortcut — a login that yields both is the floor.

Files involved (all already present):

  • .env — FABORCH_BASE_URL, SESSION_SIGNING_SECRET
  • app/api/auth/login/route.ts → lib/faborch/client.ts (foLogin) → lib/faborch/session.ts (setFoTokenCookie)
  • app/api/faborch/[agent]/chat/route.ts → foConnectedMcpIds → foChat
  • components/fab/screens/agent-chat.tsx → lib/faborch/stream.ts (readFoStream)

Request: sign in at /login with FO credentials, open /fabinsight, send “List the data sources you can query. Names only, no explanation.”

Expected: the working indicator appears within ~2 s; it names an MCP tool (e.g. cmf_list_schemas); text streams in word by word; a short list of business-named sources lands; a follow-up (“and the first one’s tables?”) works with history intact.

Pass criteria: (1) tokens arrive progressively, not all at once; (2) at least one tool-input-start is observed; (3) the FO token appears nowhere in DevTools — not in JS, not in localStorage, not in a readable cookie; (4) a follow-up carries context; (5) stop cancels and keeps partial text.

Failure readings. Answer arrives all at once → buffering in the PWA proxy or Fly, not in FO (E0 already cleared FO). “Not signed in to FabOrchestrator” → the cookie was not set; check secure vs the scheme, the exact bug isHttps() exists for. No tool line and a vague answer → activeMcpIds was empty; the connections call failed silently, which is by design and is what WP8’s guard fixes. [object Object] on screen → the nested-envelope defect; that is WP4. Nothing renders at all → the frame names moved; the parser tests will say so.

Cost: half a day, assuming the working tree builds. Value: proves every claim the architecture makes.

§21

Definition of done

Functional

  • Scanning the QR code opens the PWA; it can be installed on iOS and Android and launches in a standalone window with the app’s own icon.
  • An operator signs in with their own FabOrchestrator credentials and reaches the landing page.
  • A question typed on the landing page without choosing an agent is routed automatically, answered from the data the user is entitled to, and labelled with the agent that produced it.
  • The route can be overridden in one tap, and every agent card still either opens a working conversation or explains on the card why it cannot.
  • A prompt streams back progressively: text, tables, and artifacts.
  • Follow-up questions carry conversation context.
  • A dashboard request produces a tappable, sandboxed, light-mode artifact.
  • Stop cancels a turn and keeps what already arrived.
  • Every failure in the WP10 table renders a distinct message and a distinct next step.
  • An expired FO session produces a clean sign-in with the destination preserved.
  • Sign-out revokes the PWA session and removes the FO token from the server.

Non-functional

  • Security: the FO token is not present in client JavaScript, localStorage, any readable cookie, any log line or any service-worker cache.
  • Security: the artifact iframe has an opaque origin; window.parent.document throws inside it.
  • Security: no client-controlled field reaches an FO privilege decision — model and activeMcpIds are server-side only.
  • Boundary: no MES query, metric calculation, system prompt or model call exists in the PWA. Grep for anthropic, SELECT and system: outside the removed order workflow returns nothing.
  • Streaming: first token visible within 10 s on a normal connection; nothing buffers.
  • Tests: npm test green from a clean clone with no network; the live smoke script passes against a real FO.
  • Docs: a fresh reader reproduces the demo from the README alone.
  • Limitations written down: no file upload, no conversation history, no model picker, no offline data, time filters unvalidated, MES reachability environment-dependent.

The one-line test

A supervisor scans a code on the shop floor, installs the app, asks it what yield looked like this week, and reads FabOrchestrator’s answer — computed by FabOrchestrator, against FabOrchestrator’s data, under that supervisor’s own permissions — on their phone. Every line of this plan exists to make that sentence true without a second copy of FabOrchestrator being built to do it.
