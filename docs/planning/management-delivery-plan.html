01

Objective

Deliver an installable mobile app that lets a supervisor on the floor ask FabOrchestrator a question — about yield, downtime, quality, a production order — and read the answer on their phone, under their own permissions.

The app is a front door and a secure connector. It does not contain any manufacturing intelligence of its own. Every answer it displays is produced by the FabOrchestrator platform we already run: the AI reasoning, the connections to MES and quality data, the dashboards, the user permissions, the usage limits and the audit trail all stay exactly where they are today.

That boundary is the central design decision, and it is what keeps this project measured in weeks rather than in months. A second copy of FabOrchestrator’s logic on a phone would have to be kept correct forever, and would be wrong the first time the platform changed. This app forwards questions and displays answers.

What the app delivers

  • Reached by scanning a QR code — no app store, no IT deployment
  • Installs to the phone’s home screen and opens like a native app
  • Each person signs in with their own FabOrchestrator account
  • Ask from the landing page without choosing anything — the system works out which part of the platform should answer, and sends the request there
  • Choice of the platform’s agents by name as well, for anyone who prefers to pick
  • Answers appear progressively as they are produced, including tables and dashboards
  • Clear, actionable messages when something is unavailable

What stays in FabOrchestrator

  • All AI reasoning and model access
  • All MES, ERP and quality data connections
  • All business logic and analysis
  • Dashboard generation
  • Deciding which tools and which data answer a question
  • User roles, permissions and usage quotas
  • The audit trail of who asked what, and what it cost

An honest note on the starting point: this is not a green-field build. A working prototype of the connection between the phone app and FabOrchestrator already exists, and the estimates below reflect the effort to take each component from prototype to something we can put in front of a customer — secured, tested, documented and supportable. Where a component is already close, the estimate is small; where it is genuinely new, the estimate is larger.

02

Target architecture

Five steps, one of which is the only piece we are building.

Supervisor's phone │ types a question ▼ 1 Mobile app · the screen people use │ ▼ 2 Mobile app's secure server · the connector we build │ holds the FabOrchestrator credential; the phone never sees it ▼ 3 FabOrchestrator · the platform we already run │ AI reasoning · MES and quality data · dashboards · permissions · audit ▼ 4 The answer, streamed back word by word as it is produced │ ▼ 5 Displayed on the phone · text, tables, dashboards

Why step 2 exists

Three reasons, and each one is load-bearing:

  • Security. The credential that identifies the operator to FabOrchestrator is held on our server, never on the handset. A phone that is lost, screenshotted or handed around carries nothing that grants access to production data.
  • Necessity. FabOrchestrator does not accept direct calls from another website’s browser page. This is a deliberate protection in the platform and we are not going to weaken it — doing so would require putting that credential into the phone, which is the thing we are avoiding.
  • Control. Which data connections a question is allowed to use is decided on our server from the operator’s own permissions, not by whatever the phone sends. FabOrchestrator then checks it again independently.

Where the thinking happens

A confirmed requirement is that a user should be able to ask for what they want from the landing page and have the system decide which part of FabOrchestrator should serve it. It is worth being precise about how little of that is new, because it was checked against the platform’s own code rather than assumed:

  • Choosing the tools and the data for a question is already the platform’s job, and it already does it. When a question arrives with a user’s data connections attached, FabOrchestrator decides which plant systems to query and how. The app adds nothing here and must not try to.
  • The platform already offers a single ask box of exactly this kind on its own home screen. The interaction is the product’s, not an invention of this project. It is currently wired without data connections, which the app corrects on its own path.
  • What is genuinely missing is the choice between the platform’s several agents. Nothing in the platform decides that today; each agent is reached only from its own screen. That one decision is the new work — and even then the app asks FabOrchestrator to make the judgement rather than making it itself, so the intelligence stays in one place.

Anything unclear, unanswerable or not permitted falls back to the general-purpose agent, which answers rather than failing. The chosen route is shown on the answer and can be changed in one tap, and picking an agent by name stays available throughout.

Everything else in the diagram already exists and is unchanged by this project. No changes to FabOrchestrator are required — every service the app needs is already available and already secured the same way. Two optional half-day improvements to the platform are noted in §08; neither blocks delivery.

Phase order is set by genuine dependencies, not preference: nothing can reach FabOrchestrator before sign-in works, and plant data cannot be proven before the connection is proven. Each phase is dated by the one week in which it is finished, with one engineer at five days a week; Phases 2 and 3 both finish in week 3 because Phase 3 is small. The days shown are the scheduled figures, which include 1.5 days of environment probing and milestone demonstrations on top of the 23.0 days of build effort in §04. With two engineers the phases overlap and delivery compresses to about 4 weeks. Phase 0 is the only phase that unlocks no business capability; it is kept separate rather than folded into Phase 1 because pretending it delivers value would misrepresent what the first week produces.

Phase 1 is the decision point

By the end of week two the entire architecture is proven with a real question and a real answer from a real account, and the first business capability — secure access — is realised. Everything after that is capability and quality on a design that is already validated. If the approach is going to fail, it fails there — about a fifth of the way into the budget, not at the end.

04

Engineering components

Twelve components. Each one is a capability the app cannot ship without, and each estimate is the effort to bring it to a state we would demonstrate to a customer.

ComponentWhat is built Why it is neededDeliverable Days
C1  Baseline & environment validationWP0 Consolidate the codebase into one reviewable branch, and run five short live checks against the running FabOrchestrator to confirm the environment behaves as the design assumes. Four of the six things that could delay this project are properties of the running system, not of our code. Confirming them in the first two days is the cheapest risk reduction available — it converts guesses into facts before anyone commits to a date. A single build-able codebase, and a one-page report answering the five environment questions with evidence. 0.5
C2  Mobile app foundation & installabilityWP1 The phone-shaped shell: screen layouts that work one-handed, and the packaging that lets the app be installed to a home screen from a QR code and open in its own window. This is the difference between “a website” and “an app” to the person holding the phone, and it is the whole reason we chose this delivery route over a native app. Getting install behaviour right on iPhone in particular takes hands-on work — Apple gives us no automatic prompt, and the failure modes only appear on a real device. An installable app, verified on one iPhone and one Android handset, that behaves sensibly when the network drops. 1.5
C3  Sign-in & session securityWP2 Each user signs in with their own FabOrchestrator account. Their credential is exchanged for a revocable session held on our server; the phone receives only a meaningless identifier. Sign-out, expiry and re-authentication are handled cleanly. Every question must be attributable to a real person, because FabOrchestrator applies that person’s permissions, data access, usage limits and audit record. A shared demo account would hand whoever holds the QR code somebody else’s access to production data, and would make the audit trail worthless. Working sign-in and sign-out; the FabOrchestrator credential provably absent from the phone; a clean re-authentication prompt when a session ends. 2.5
C4  Secure connector to FabOrchestratorWP3+WP4 The single server-side component that knows how to talk to FabOrchestrator: sign in, ask which data connections a user has, forward a question, pass the answer straight back, and translate any platform error into something the app can act on. It is the only place in the app that knows FabOrchestrator’s interface. Keeping it in one component means that when the platform changes, exactly one thing has to change with it. Spreading that knowledge across the app is how integrations become expensive to maintain. One connector carrying all agent traffic, with every failure returning a predictable, displayable message. 2.0
C5  Live answer streamingWP5+WP6 Reading FabOrchestrator’s answer as it is produced and showing it word by word, plus carrying the conversation so follow-up questions work. A question that involves looking up plant data can take one to three minutes. Waiting in silence for that and then showing everything at once reads as a broken app. Progressive display is the difference between a system that feels responsive and one that feels hung — and it is the single most visible quality signal in a demo. Answers that appear progressively, survive a poor connection, can be stopped mid-answer, and support follow-up questions. 1.5
C6  Agent selection & access controlWP7 The landing screen presenting FabOrchestrator’s agents, each routed to the right service, with the one permission-gated agent shown as unavailable when the platform’s own permission check says so. Only one agent — the Modeling Agent — requires a role permission, and FabOrchestrator itself enforces it by refusing the request. The app adds presentation, not authorisation: asking the platform up front turns a mid-conversation refusal into a labelled card, which is the difference between a closed door and a broken one. An agent menu where every entry either opens a working conversation or explains why it cannot. 1.0
C7  Operational data answersWP8 Making sure a question about the plant actually reaches live MES and quality data, and that the resulting figures and tables are readable on a small screen. This is the demo. It is also the most fragile link, because FabOrchestrator only queries the data connections that are explicitly enabled for that user — if none are, the platform still answers, but from general knowledge rather than from the plant. That failure looks like a wrong answer rather than a missing permission, so the app must detect it and say so. A metric question answered from live plant data on a phone, with wide tables that remain readable, and an explicit warning when a user has no data access. 1.5
C8  Dashboard & visual outputWP9 Displaying the charts and dashboards FabOrchestrator generates, inside a security container that isolates them from the rest of the app, sized for a phone. Dashboards are FabOrchestrator’s most persuasive output and the platform produces them in two different forms, which the app has to handle differently. It is also the most security-sensitive part of the build: a generated dashboard is live, interactive content, so it must be strictly isolated from the app’s screens and credentials. That isolation, plus making a desktop-shaped chart usable at phone width, is what makes this the largest component. A dashboard request produces a tappable, full-screen chart on the phone, verified to be unable to reach the app around it. 3.0
C9  Progress & failure handlingWP10 What the user sees while waiting, and what they see when something goes wrong: an expired session, a permission they lack, a usage limit, an unreachable data source, a dropped connection. This app sits in front of a live production platform, so failures are normal operating conditions, not edge cases. Each one has a different correct response — sign in again, ask an administrator, try later, retry now. A single “something went wrong” sends the user to find whoever set the demo up, which in a customer meeting is the failure that matters. Every identified failure produces a distinct, plain-language message with a clear next step, plus a reference code support can trace. 2.0
C10  Test suite & verificationWP11 Automated tests for each layer separately, a simulated FabOrchestrator so the app can be tested without one, and a scripted live check against the real platform. The chain has five links and two of them — the platform and the plant data — are outside this team’s control and are not always available. Without layer-by-layer tests, every fault looks identical and diagnosis is guesswork. This is also what makes the app maintainable after handover rather than a demo that decays. A test suite that runs from a clean checkout with no network, plus a live check script that pinpoints which link in the chain has failed. 3.0
C11  Device validation, security review & handoverWP12 End-to-end validation on real handsets, a security review, configuration and logging cleanup, setup documentation, a written demo procedure and a stated list of limitations. The app touches a production identity system and production data, so it needs a review before it is shown outside the team. And a demo nobody but its author can run is not a deliverable — the runbook and documentation are what let this be presented, and supported, by someone else. Signed-off security review; README that a new engineer can follow; one-page demo runbook; written limitations. 2.5
C12  Agentic entry pointWP13 An ask box on the landing screen that takes a plain request, works out which part of FabOrchestrator should serve it, sends it there, and shows which one answered — with one tap to send it somewhere else instead. Confirmed requirement: people should not have to know the product’s internal structure to ask a question, and on a phone the choice costs a screen before anything is typed. Checked against the platform’s code first: choosing the tools and the data for a question is already the platform’s own work, so the only genuinely new decision is which agent — and even that judgement is asked of the platform rather than made in the app. A landing question answered without an agent being chosen, labelled with the agent that served it and correctable in one tap, with agent-by-name selection still working. 2.0

Four of the six drivers above are answered by the environment checks in component C1 — half a day of work, run in the first two days. Principal risks

Automatic routing can send a request to the wrong agent

Some requests genuinely sit between two agents, and the platform has no router of its own whose accuracy we could inherit. Four things keep this from being a delivery risk: the default is the agent that can answer the widest range of questions, so an unclear request still gets answered; the agent that served the answer is shown, and can be changed in one tap; picking an agent by name remains a first-class path; and a fixed set of about twenty real questions is scored, so accuracy is a number we can watch rather than an anecdote. No contingency is held against it — it is our own code, not an external dependency.

RiskImpact if it occursHow we handle it
Hosting layers hold answers back instead of streaming them High The app works but feels broken — a two-minute silence then a wall of text. The most visible quality of the product is lost. Checked in week one, before anything is built on the assumption. If it fails, it becomes an infrastructure request, raised early rather than discovered at the demo.

Worst case, this is discovered in front of a customer. Checked in week one. The app is also built to detect it and say so explicitly rather than answer anyway.
The generated dashboard container is misconfigured High if wrong A generated dashboard is live interactive content. Weak isolation would let it reach the app around it. Isolation is a fixed rule in the design, verified by an automated test that attempts to break out and must fail.

The app handles it cleanly — sign in again and continue where you were. Worth briefing whoever runs the demo. Changing the 30-minute policy is a platform decision, not ours.

Two decisions — both now taken

1. Scope of the app — decided 1 September 2026. The codebase also carried a separate production-order review workflow that ran on sample data and did not connect to FabOrchestrator. It has been removed, along with the second sign-in route it needed, so the app is one clear thing: a mobile front door to the platform. The estimate does not change — it already assumed this; the 3 days quoted were the cost of keeping the workflow, and are not incurred.

2. Which platform the demo runs against — decided 1 September 2026. The live deployment. Every environment check and the end-to-end architecture proof have run against it. The concern that it lagged the current code is largely spent: the one service believed to be missing turned out not to exist in the platform at all, so its absence was correct behaviour rather than drift.

Two optional half-day improvements to FabOrchestrator itself were identified — correcting an out-of-date interface document, and adding a simple availability check that would let the app distinguish “the platform is down” from “your session expired”. Neither is required for delivery; both would need the platform team’s agreement.

09

Definition of done

The project is complete when all of the following are true and demonstrated.

The app works

  • Scanning a QR code opens the app; it installs to the home screen on iPhone and Android and opens in its own window.
  • A user signs in with their own FabOrchestrator account and reaches the landing screen.
  • A question asked from the landing screen, with nothing selected, is routed to the right part of FabOrchestrator, answered, and labelled with which one answered it — and the route can be changed in one tap.
  • Every agent is also reachable by name, and either opens a working conversation or states why it is unavailable.
  • Answers appear progressively — text, tables and dashboards — and follow-up questions keep their context.
  • A metric question returns figures drawn from live plant data.
  • Every failure produces a clear message and an obvious next step.
  • Sessions expire and resume cleanly; signing out ends access.

It is safe and supportable

  • The FabOrchestrator credential is provably absent from the phone.
  • Generated dashboards are verified isolated from the app around them.
  • No permission decision can be influenced by anything the phone sends.
  • The app contains no plant logic, no data queries and no AI reasoning of its own — the boundary the project was built on is verifiable, not just intended.
  • Automated tests run from a clean checkout with no network access.
  • A security review is signed off.
  • A colleague reproduces the full demo from the written documentation alone.
  • Limitations are written down, not discovered by a customer.

The one-sentence test

A supervisor scans a code on the shop floor, installs the app, asks what yield looked like this week, and reads FabOrchestrator’s answer — computed by FabOrchestrator, from FabOrchestrator’s data, under that supervisor’s own permissions — on their phone. Every component in this plan exists to make that sentence true without a second copy of FabOrchestrator being built to do it.
