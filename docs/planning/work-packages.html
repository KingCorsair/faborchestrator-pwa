Implementation plan · planning table

FabOrchestrator PWA Work Packages

The engineering work required to deliver the mobile app, in build order, grouped into the business-value phases. Estimates are engineer-days. Each row carries both its technical milestone and the business phase and milestone it serves. Technical milestones M0–M5: M0 baseline confirmed · M1 architecture proven end to end · M2 all agents reachable, chosen or routed · M3 real plant data on a phone · M4 dashboards and failures behave · M5 ready to hand over. Business milestones: B1 secure access · B2 ask-first conversations · B3 plant value on mobile · B4 operational output · B5 reliable use and handover. Phase 0 carries no business milestone — it removes uncertainty rather than delivering capability.

PHASE 0Foundation and proven linkdone in week 1 · closes M0No business capability yet, by design. What this phase buys is certainty: one codebase the team can build, evidence of how the live platform behaves, and answers arriving as they are written.
1 WP0Baseline & environment validation Branch consolidation + live environment probes Bring the code onto one reviewable branch and run short checks against the running FabOrchestrator to confirm it behaves as the design assumes. Several things that could delay the project are properties of the live environment, not our code. Checking them first turns assumptions into facts. One build-able codebase, plus a one-page report evidencing how the live platform actually behaves: streaming, data access, deployment currency and demo-account readiness. M0 ✓completes M0 P0foundation — no business capability by design 0.5
2 WP6Live answer streaming Server-Sent Events stream parser Reading the platform's answer piece by piece as it is generated and putting each piece on screen as it arrives. A question involving plant data can take one to three minutes. Silence followed by a wall of text reads as a broken app. Answers that appear progressively, survive a poor connection, and detect a stalled stream. M1contributes — streaming P0foundation 1.0
3 WP3Platform client layer FabOrchestrator API client module One server-side component that owns every call to the platform and turns platform errors into something the app can display. Keeping that knowledge in one place means exactly one thing changes when the platform changes, instead of a dozen. A single client module carrying every platform call, with all errors reduced to one predictable shape. M1contributes — platform link P0foundation 1.0
PHASE 1Secure access to FabOrchestratordone in week 2 · closes M1 & B1A named person can reach FabOrchestrator through the app and hold a live conversation, under their own account and their own permissions — with the platform credential held on our server, never on the handset.
4 WP2Sign-in & session security Credential exchange + server-side session store + httpOnly cookie Users sign in with their own FabOrchestrator account; the credential stays on our server and the phone holds only a meaningless, revocable identifier. Every question must be attributable to a real person, because the platform applies that person's permissions, data access, usage limits and audit record. Working sign-in, sign-out and session expiry; the platform credential provably absent from the phone. M1contributes — identity P1contributes to B1 2.5
5 WP4Secure connector Authenticated reverse-proxy route, streaming pass-through The backend route that forwards a question to the right agent and pipes the answer straight back without holding on to it. The platform does not accept direct calls from a browser page; this hop keeps the credential and the permission decisions on our server. A live, streaming conversation with FabOrchestrator through the app, demonstrated end to end. M1 ✓completes M1 P1B1 ✓unlocks secure access 1.0
PHASE 2Usable and agentic conversationsdone in week 2 · closes M2 & B2A user can ask from the landing page without choosing anything and the system routes the request to the right agent, follow-up questions work, and every agent is still directly reachable by name for anyone who prefers to choose.
6 WP5Conversation handling Client-side conversation state + message-history payload The app keeps the thread and sends the whole conversation with each new question, so the platform has context for follow-ups. One question is rarely enough. Follow-ups are how a supervisor actually arrives at a usable answer. Multi-turn conversations that survive interruption and can be stopped mid-answer without losing what arrived. M2contributes P2contributes to B2 0.5
7 WP7Agent selection & access control Agent registry, endpoint routing A fixed list mapping each agent to its own platform service. The availability query it also carried is gone — see right. Reduced by a product decision, 2 September. The availability query existed for one agent: the Master Data Load Agent was the only permission-gated one. Jothi confirmed it is not part of this app, and the platform’s remaining chat endpoint does not refuse on permissions at all — so there is nothing left to ask about. The registry and endpoint routing were already built under WP3 and WP4. An agent menu where every entry either opens a working conversation or says on the card that this app does not open it. Delivered 2 September, verified in a browser: the Master Data Load Agent card is shown, greyed and not openable, and its route is gone. M2 ✓contributes — agent menu P2contributes to B2 0.5was 1.0
8 WP13Agentic entry point — ask first One ask box on the landing screen The user types what they want and the system works out which tools and which data should answer it, then returns the answer. No classification layer was needed. Met without building anything, 2 September. Two things were being called routing. The platform’s own chat endpoint already picks the caller’s authorised tools and data per question, over up to twenty steps — that half was never this project’s work. The other half, choosing between agents, disappeared when the Master Data Load Agent left: every remaining agent is the same service, so there is nothing to choose between. A landing question answered without an agent being chosen, with manual selection still available. Verified in a browser against the live platform, 2 September. The “labelled with the agent that served it” clause is moot with one destination and returns if a second is ever exposed. M2 ✓completes M2 P2B2 ✓unlocks ask-first working 0was 2.0
PHASE 3Real plant value on mobiledone in week 3 · closes M3 & B3A supervisor installs the app from a QR code and asks real MES and quality questions from the floor — yield, downtime, scrap — and reads the answer as a table on their phone. This is the phase the business case rests on.
9 WP1Mobile app foundation Web app manifest, service worker, responsive layouts The packaging that lets a phone install the app to its home screen and open it in its own window, plus screens that work one-handed. This is what makes it an app rather than a website, and why no native mobile app has to be built or distributed. An installable app, verified on one iPhone and one Android handset, that degrades honestly when the network drops. M3contributes — installability P3contributes to B3 1.5
10 WP8Live plant data answers MCP data-connection resolution + markdown table rendering Look up which MES and quality data connections the user is approved for, pass them with the question, and render the resulting tables readably on a phone. This is the core demonstration. The platform only queries the data connections explicitly enabled for that user, so the app must confirm they exist rather than answer without them. A metric question — yield, downtime — answered from live plant data on an installed handset, as a readable table. M3 ✓completes M3 P3B3 ✓unlocks plant value on a phone 1.5
PHASE 4Rich operational outputdone in week 4 · closes M4 & B4Answers stop being only text: dashboards and charts open full-screen, progress is visible while a long question runs, and every failure explains itself and says what to do next.
11 WP9Dashboard & visual output Artifact tag parsing + sandboxed iframe rendering Pull the generated chart or dashboard out of the answer and display it in an isolated frame that cannot reach the app around it, sized for a phone. Dashboards are the platform's most persuasive output, but they are live interactive content and must be strictly isolated from the app and its credentials. A dashboard request produces a tappable, full-screen chart on the phone, verified unable to reach the app around it. M4contributes — visuals P4contributes to B4 3.0
12 WP10Progress & failure handling Normalised error contract + streaming progress states One predictable shape for every failure the app can hit, and distinct indicators for waiting, working and answering. The app fronts a live production platform, so failures are normal operating conditions, and each one needs a different response from the user. Every identified failure produces a distinct plain-language message, a next step, and a reference code support can trace. M4 ✓completes M4 P4B4 ✓unlocks operational output 2.0
PHASE 5Ready for reliable use and handoverdone in week 5 · closes M5 & B5The app can be run, supported, demonstrated and maintained by people who did not build it — tested, validated on real handsets, security-reviewed, documented.
13 WP11Test suite & verification Unit and route tests, stub platform, live smoke script Automated tests for each layer on its own, a simulated FabOrchestrator so the app can be tested without one, and a scripted check against the real platform. The chain has five links and two are outside our control. Without layer-by-layer tests every fault looks identical and diagnosis becomes guesswork. A test suite that runs from a clean checkout with no network, plus a live check that pinpoints which link failed. M5contributes — verification P5contributes to B5 3.0
14 WP12Device validation, security review & handover Device QA, security review, config hygiene, runbook End-to-end validation on real handsets, a security review, cleaned-up configuration, setup documentation and a written demo procedure. The app touches production identity and production data, and a demo only its author can run is not a deliverable. Signed-off security review, setup documentation a new engineer can follow, and a one-page demo runbook. M5 ✓completes M5 P5B5 ✓unlocks reliable use 2.5

Rows are in build order, set by real dependencies — nothing can reach FabOrchestrator before sign-in works, and plant data cannot be proven before the connection is. WP numbers are stable identifiers from the engineering plan, so they do not run in sequence here. A milestone marked ✓ is completed by that package, and each phase ends on the package that completes its milestone. WP13 was the newest package: the confirmed requirement that a user can ask from the landing page without picking an agent first. It closed on 2 September without a line of routing code, when Jothi confirmed the Master Data Load Agent is not part of this app and every remaining agent turned out to be the same platform service. WP7 shrank for the same reason. 2.5 days came out of the core estimate, and 4.0 of the 9.0 contingency days were released by the 1 September environment checks — but the finish still lands in week 5, because 22.0 days is 4.4 weeks. What the saving bought is margin before that date, not an earlier one. Each phase is dated by the one week in which it is finished, on the 22.0-day schedule (which carries 1.5 days of probe and demonstration work on top of the 20.5-day package estimates); phase 2 now finishes in week 2, and phase 3 in week 3. Sequence shown is for one engineer; with two, steps 2, 9, 11 and 13 can start earlier.
